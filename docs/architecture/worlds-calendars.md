# Worlds calendars: creator and historical evolution

Start at 9617b32, with the journal ending at 0099. Preserve canonical version-1 world years and Pass 2A reckonings. Calendar years do not imply world years or a universal day length. The older StFinal creator was reviewed: named months/weekdays, optional day units and cultural observances are useful; descriptive previews, free-text leap expressions, global ownership and celestial controls are not carried forward.

## Working checkpoints

A delivers world-owned calendar identities and immutable structural versions, validated calculations, gallery, contextual rule authoring, navigable actual month/year previews, weekday rules, time units, intercalation, seasons and recurrence. Version copies are independently readable. A has a complete migration, upgrade/role/conflict/database/browser/build verification and local commit before B begins.

B adds explicit world elapsed-day origins, version anchors, effective periods, adoption labels, reform relationships and precise History references. Exact days are stored as decimal integers with BigInt arithmetic. A version needs an authored anchor to convert; an effective year interval does not establish a day-level transition. Cross-version notation ambiguity remains explicit. Historical precision and canonical ordering never gain fabricated days. B follows A's committed migration with a complete additive migration and independently working interfaces.

## Creator rule grammar

Version-1 definitions contain 1-40 named months of 1-400 ordinary days, 1-20 named weekdays, year-zero/no-zero numbering, continuous/year-reset/month-reset weekday progression and a zero-based weekday origin at the beginning of the epoch year (0, or 1 when zero is excluded). Optional day units are explicitly authored positive integer hours/day and minutes/hour, without weather mechanics.

At most 20 named intercalary days each specify insertion after an ordinary month/day (day 0 means before that month's first ordinary day), participation in the weekday cycle and a periodic rule. Periodic rules match printed year minus offset modulo every N; optional exception multiples and restoring multiples must nest exactly. Bounded explicit included/excluded years override that rule; contradictory years are rejected. Every 1 is annual. No arbitrary code or natural-language expression is executed. Added days have stable IDs and separate notation instead of changing the meaning of ordinary month/day labels. Maximum authored year size is bounded; larger definitions fail visibly.

Seasons use explicit ordinary month/day boundaries, may wrap the year and overlap, and need not number four. Observances support annual month/day, actual ordinal day of the year, and a named intercalary day, with their own periodic rule. A skipped recurrence has no occurrence that year. Invalid ordinary boundaries are rejected. No shortened ordinary month can silently normalize a date. The preview shows the actual days, participating weekdays, out-of-week days, season names and observed festivals/holidays/recurrences.

Year prefixes count periodic matches with integer floor division and explicit exception adjustments; they never traverse elapsed years. Date lookup within a year is bounded by authored year size; inverse lookup uses bounded binary search over supported signed years. No JavaScript Date is used for fantasy time. All elapsed-day arithmetic uses BigInt internally, and strings across JSON. Calendar years support the same signed trillion-year range while legacy canonical years keep their own meaning.

## Persistence and authorization

Reuse the Worlds service actor/owned-world transaction lock and private HTTP wrapper. Calendar identities and versions have same-world composite keys; default preference references a version in that world. All structural definitions are immutable after save: revision creates another version. Metadata/lifecycle/default writes have revision checks. Archive retains rules and blocks new uses until restored; explicit Administrator review remains read-only. Owned-World account-deletion protection covers descendants without new User FKs. Each migration is additive, versioned and tested with existing data. Reverting code does not reverse schema; retain metadata and pause incompatible writers during recovery. No remote push, Production migration or deployment is authorized.

## Checkpoint B: historical evolution and exact notation

Migration 0101 follows 0100 and adds six operational tables: `world_day_reference`, `world_calendar_anchor`, `world_calendar_history`, `world_calendar_adoption`, `world_calendar_reform` and `world_calendar_entry_date`. It changes no existing columns or rows. Every version, linked entry and precise source association has a composite same-world FK. Anchors additionally require the world's authored day reference; precise History sources require anchored versions. Existing owned-World account deletion protections continue to cover these descendants.

One immutable World reference describes elapsed day 0 and the common day unit. Each version may have one immutable anchor pairing an actual printed calendar date with a canonical decimal elapsed-day string. The author explicitly confirms that each ordinary or intercalary day counts one common day. Optional hours/minutes do not establish physical equivalence. No World-year or year-reckoning offset supplies an anchor. Origins and anchors are immutable through application commands; mistakes or repeated epochs require a distinct definition/World rather than reinterpretation of old records.

Serializable elapsed days match `0` or an optional minus sign followed by one through twenty digits, with no leading zeros. Arithmetic uses BigInt exclusively. Conversion adds the intrinsic difference from the source anchor, then resolves the target date by bounded inverse lookup. Both anchors, explicit version IDs and real supported dates are required. Missing anchors, absent intercalary dates, malformed integers and positions beyond a version's supported signed trillion-year range fail explicitly. Browser selectors qualify versions, and numbered months/named insertion IDs distinguish otherwise repeated names. Free-text date labels are never treated as unique occurrence identifiers.

Version histories and adoptions retain canonical World-year precision: known/approximate years, uncertain windows, durations or unknown time. An explicit open-ended flag describes a beginning with no recorded end; a known duration cannot also claim an unknown end. Authored usage labels have stable record IDs so future structured actors can connect through additive relationships without destroying labels. Overlap is allowed. Preferred display is independent of adoption. A year filter shows potentially matching authored periods and keeps unknown periods visible; uncertain bounds do not prove exact usage.

Reforms reference predecessor/successor versions, authored canonical effective time, reason, transition details and an optional existing History ID. The existing account/narrative status is read by reference rather than copied or rewritten. An optional cutover snapshots two explicitly anchored dates and requires successor day = predecessor day + 1. Skipped or repeated printed labels retain separate version identity while elapsed chronology continues. A reform without those explicit dates has no precise cutover. Reforms/adoptions are append-only accounts with revision-checked archive/restore; corrections can retire a record and add another. Version-context edits have independent revisions. Reforms describe a transition, not a global prohibition on other groups continuing to use an earlier calendar.

An optional History child row snapshots known, approximate, uncertain-window or duration notation, calendar name, version title/ID, structured month/day/insertion identity, anchor-derived elapsed position and boundary context. Server snapshots cannot be supplied by clients. Windows/durations may cross reforms and cannot end before they begin on the shared day reference. Identity renames, retirement, display preferences and new rules never change saved source meaning. Existing unchanged references can be retained after archival; new dates/uses require active definitions. Omitted fields from older clients retain sources; explicit null clears the optional context inside the entry's revision-checked transaction.

Canonical `historical_time` and year-reckoning source remain independent. Adding a calendar source never changes them. An exact calendar day with no authored World-year relationship remains outside the year timeline, with its canonical year explicitly described as unknown. Canonical sorting is unchanged and never mixes elapsed days with unanchored year-level records. Original and equivalent notation/boundaries are readable in History details; estimated points/windows remain uncertain after conversion. Calendar histories link relevant existing accounts without merging planned development into recorded history. No Campaign, combat or environmental time advances.

Recovery is additive: reverting code does not undo 0101 or erase sources. Keep reference/anchor/rule/source tables and the migration ledger intact. Older code can still read original World rows, but cannot present the new context; pause incompatible History/calendar writers during rollback and prefer a forward fix. Backup restoration requires stopped writers, a verified target, reconciliation of subsequent data and matching code/ledger.
