# Owned Creatures Upgrade Pass 3

The management system now supports binding from either the Creature or the exact empty Vessel copy, with one authoritative relationship and one existing disposition command. Campaign-owning G.O.D.s can inspect retained unowned profiles in both NPC editors, histories show readable before/after details, and duplicate names remain distinguishable. Gameplay runtime is deferred.

1. **Commit / push SHA.** Approved base: `7d9823fccae6594b1e44cead7b474a0fef57b59b`. The delivery message records the exact pushed Pass 3 SHA. The commit containing this report is the completed pass; `git log -1 --format=%H -- docs/architecture/owned-creatures-pass-three-report.md` identifies it without a self-referential hash inside the commit. Main was fetched and matched the approved base before committing.

2. **Files changed.** [changed-files.txt](../samples/owned-creatures-pass-three/changed-files.txt) lists every delivered path. The existing owner authorization and disposition read projection are shared with the inverse chooser; the existing mutation remains the only binding writer. New components handle retained inspection and Vessel-side selection. Shared profile history is projected once and rendered in both owned and unowned views. Character and detailed NPC exact-copy rows reuse the same Vessel component. Scripts, guidance, handoff, checklist and curated evidence complete the pass.

3. **Migration status.** No new migration or schema change. Migrations 0088 and 0089 are unchanged. All 90 migrations replayed on a fresh disposable database; the existing populated 0088 → 0089 rehearsal again preserved all 195 prior public tables. Shared environments were not migrated.

4. **Final management model.** Ownership remains solely `owner_character_id`; disposition remains normal travel; the Companion Profile records intended roles/behavior. Exact Vessel bindings remain in `owned_creature_disposition`. Empty Vessel acquisition and later binding are supported. On an eligible exact copy, **View Vessel binding → Bind Creature → choose an individual → Save Vessel binding** submits the same command as Creature-side management. It creates neither an individual nor ownership. The chooser excludes already-bound Creatures and makes the change from Not Yet Set/Accompanying/Away explicit. It has no parallel model or Item-binding event stream.

5. **State presentation.** Verified Not Yet Set, Accompanying, Away and Vessel-bound; absent, notes-only, configured and review-required profiles; no bond, accessible bond, contained/closed/inaccessible copy, dropped/lost/stolen copy, held-elsewhere copy and archived definition retaining its bond. The retained inspector states unassigned ownership and Not Yet Set current travel, with prior travel available in history. Archived definitions are now named explicitly in custody text. None of these labels promises runtime availability. Notes-only profiles still clearly say behavior is unconfigured.

6. **Multiple companions.** Three same-master, same-name individuals were configured independently with the requested A/B/C role/control/preference/disposition combinations. Later edits and bindings on one preserved the others' rows and histories. No owner-wide active-companion, Mount, Familiar, stored-Creature or deployment limit was added.

7. **Duplicate Creatures and Vessels.** Exact IDs resolve every relationship. Reverse lookup and the inverse chooser now show `Creature name · Individual #ID`. Existing Vessel copy labels remain stable and distinct for duplicate definitions/names. Tests covered two same-name choices, multiple copies of one definition, one winner when two individuals claim a copy, and one winner when two copies are chosen for one individual. Desktop and phone browser checks exercised duplicate choices.

8. **Ownership review.** Settings survive removal/reassignment with `requires_owner_review`. Owned views explain that retained settings are not approved for the current owner. Unowned views explain that approval follows assignment. G.O.D. must explicitly confirm; Players can change notes without clearing review. Historical before/after details normalize both application and trigger snapshots and identify the previous/new owner by stable Character number, including unassigned.

9. **Actor attribution.** Deferred deliberately after auditing direct assignment, initial creation, sale, exact resale and lifecycle cleanup. Existing triggers directly insert immutable null-actor records and have no authenticated-actor context hook. Retrofitting application receipts would duplicate history or require changing the database trigger contract. Resale's `ownerUserId` is not safely interchangeable with the actual executing actor; the outer commerce operation has its own actor/operation receipts. Old records were not rewritten, triggers were not weakened, and no actor was guessed. Future automatic ownership companion events still explicitly say actor not recorded; ordinary authored travel/profile/Vessel-side saves retain authenticated attribution. The [handoff](owned-creatures-runtime-handoff.md#why-automatic-ownership-events-remain-unattributed) records the exact paths and a future design boundary.

10. **Unowned retained-profile inspection.** Added a read-only, exact-Creature server path restricted to the Campaign-owning G.O.D., with Campaign-first locking consistent with ownership changes. Both simple and detailed editors reuse it. It exposes retained roles, choices, Mount fields, relationship notes, review state, profile history and prior travel history. It works for archived retained records. Players without ownership, administrator-only actors, foreign G.O.D.s, non-Creatures and now-owned targets reject. No fake owner or mutation authority is created.

11. **History.** Two streams remain separate. Each shows revision, timestamp and truthful actor attribution. Travel displays before → after, including exact copy identity and Away notes. Profile events now have expandable before/after roles, control, preference, Mount data, relationship notes and review state. Ownership summaries identify the transfer/removal. The deliberate latest-30 boundary was tested with 31 stored events in each stream; no pagination or data pruning was added. Item names reflect current definitions when available.

12. **Reverse Vessel lookup and binding entry.** Read projection contains only the readable copy label, bound Creature name/individual token, and a binding-entry availability flag. No private NPC notes, hidden mechanics, health/resources or owner-edit controls. Holder authorization is checked server-side; a stale holder loses access. New binding requires enabled capability, a live exact copy and definition, correct owner inventory and accessibility. The inverse chooser reuses Creature-side eligibility and save protections. Inaccessible/closed, retired, archived, wrong-holder, disabled and occupied copies reject; existing custody-safe bonds remain readable. Existing lookup in Character/Race-NPC Item-copy rows and the added detailed Creature inventory lookup share one component.

13. **Player permissions.** Existing current-owned read/rename/travel permissions remain. Players may bind through either entry point and edit relationship notes; they cannot configure roles, Control Model, Combat Preference, rider capacity or owner review. Forged server commands and unrelated-Player requests reject. Profile code retains the previous Player-plus-admin protection. Failed binding retains the exact command for retry; refresh reads a new revision rather than silently overwriting.

14. **G.O.D. permissions.** Campaign-owning G.O.D. can configure and manage permitted active companions, bind through either entry point, explicitly review transfers and inspect retained unowned settings. Administrator/library authority alone and foreign G.O.D.s gain no management authority. Existing active/paused Encounter guards remain authoritative on the server. The Item-side UI adds no weaker mutation endpoint.

15. **Race NPC owners.** Tested retained-role review after reassignment to a Race NPC, G.O.D. Mount/Familiar configuration, inverse chooser and exact binding, and Player denial. This uses the same owner relation and profile/disposition tables; no NPC-controller-based Player powers are inferred.

16. **Evolution / Return.** Actual execution and historical Return preserve exact individual identity, owner, disposition, Vessel bond, roles, control/preference, Mount fields, relationship notes, review-required flag and both complete history streams. The dedicated Pass 3 case deliberately kept review pending through Evolution and Return. The full existing Evolution/Forms regressions also passed. No reclassification from the destination master occurs.

17. **Archive / restore.** Existing tests and added cases cover owner, Creature, Campaign and Vessel-definition archive/restore, retained inspection while unowned/archived, unchanged history/configuration and rejected inactive-record mutations. Exact copies use existing retirement/destruction semantics, not an invented archive feature. Bound-copy removal/retirement/destruction remains blocked. Full lifecycle cleanup still works. A bound Creature must be deliberately unbound before transfer; atomic Creature-plus-Vessel transfer remains an unanswered future question.

18. **No hidden role mechanics.** Profile changes across every role and all control/preference combinations alter only profile configuration/history. The additional 198-table comparisons cover mixed travel/profile/binding operations. Attributes, Skills, protection, carrying state, snapshots, attacks, abilities, HP and owner mechanics remain unchanged. No role is consumed by newly added gameplay execution code.

19. **Runtime-table proof.** [no-runtime-proof.json](../samples/owned-creatures-pass-three/no-runtime-proof.json) records 14 management scenarios comparing every row in all 198 public tables before/after. The strict allowlist is the five companion disposition/profile/history tables. Explicit ownership tests additionally allow only the selected individual's `owner_character_id` and `updated_at` columns; every other Character column must match. The comparison covers Sessions, Scenes, Encounters/participants, Initiative, rolls, declarations, pending actions, HP/injuries, Mana, conditions/modifiers, authored Creature attacks, execution/effect plans and all existing ability/Form-related tables or snapshot fields, including empty tables where no active runtime fixture exists. No separate mounted-state structure was found and none was created. Existing lifecycle/custody/Evolution operations intentionally write their own domains and have separate preservation tests; their writes are not disguised as companion-only operations. The proof includes inverse binding, retries, concurrent winners, authorization denials, owner review and retained inspection.

20. **Runtime handoff.** [owned-creatures-runtime-handoff.md](owned-creatures-runtime-handoff.md) is the dedicated contract document. Future runtime must consume the current exact individual, including snapshot/Evolution state, HP/injuries, effects, inventory/equipment and authored attacks/abilities. Entering play must never rebuild from the master. Vessel association is distinct from ordinary Container contents; disposition is distinct from presence; intent is distinct from execution.

21. **Unresolved runtime decisions.** The handoff reserves Scene arrival/departure, automatic presence, combat prompts, Player Directed authority, Owner Commands/G.O.D. workflows, multiple active Creatures, release/recall/costs, inaccessible/stolen/non-owner Vessel use, injured recall, stored durations, Vessel destruction, mounting/dismounting/shared movement/rider enforcement/combat, Familiar powers, atomic transfer, capture, mid-combat ownership, active Forms, combat Evolution/Return and Creature Special Ability execution. Its capture contract says legitimate acquisition/ownership must precede binding the exact individual through the existing contract, in a future coordinated transaction. Capture rolls, eligibility, resistance, costs, ownership timing, failure and combat timing remain undecided.
