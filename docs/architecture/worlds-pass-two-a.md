# Worlds Pass 2A: chronology and dating systems

The baseline is `c37bcf5`; the checkout is clean and the migration journal ends at 0098. Pass 2A adds named year reckonings to existing worlds without changing the Registry or creating calendars, Atlas, public access or runtime timekeeping.

## Time boundaries

1. Canonical historical time stays version 1 `world-year`: signed whole years within ±1 trillion, including Year 0, and the existing known/approximate/window/duration/undated representations. Existing rows and ordering are never rewritten.
2. A world-owned reckoning maps those indices to signed displayed year numbers. Its epoch is the canonical index of displayed Year 0 (year-zero convention) or Year 1 After (no-year-zero convention). With delta = canonical minus epoch, year-zero displays delta; no-year-zero displays delta when negative and delta + 1 otherwise. The inverse rejects displayed zero for no-year-zero. Labels explicitly describe Before/After; display arithmetic remains safely inside JavaScript's integer range.
3. Future calendars are independently authored structures, not aliases for reckonings. Their variable year lengths/month/day precision must introduce explicit mappings and precision types. Legacy year-only records will continue to identify a whole canonical historical year or interval; they will never acquire a fabricated month/day.
4. Future absolute elapsed-time and Campaign clocks require separate units, mappings and authorization. This pass has no such reference or mutation path.

## Persistence and safeguards

Add a world dating-system table, a world chronology-preference table (nullable default means canonical fallback), and nullable source-system/snapshot columns on historical eras and entries. Composite foreign keys enforce same-world source and default references. A snapshot records the original convention identity, revision, arithmetic, labels and displayed source years. Older records have no source context and keep their original dates.

All writes use the existing current-role checks, owned-world transaction lock, revision checks and archive rules. Once first referenced by an authored date, a system's epoch and numbering rule are permanently immutable. Names/descriptions/labels/notes remain editable; saved source snapshots preserve earlier wording. Referenced archived systems remain readable and usable for retaining existing references, but cannot receive new references or become the default. Switch the default before archiving it. Default changes increment the world revision and never update historical rows. Existing account-deletion protection through the owning World covers chronology; no new User FK or ownership model is introduced.

## Interface and validation

Add a Chronology workspace with cards, origin/numbering examples, reversible interactive conversion and contextual native-modal editing. Use semantic theme variables and shared field guidance. The canonical convention is always usable without configuration. History, overview preview, timeline ticks/details/list and year navigation share selected display formatting; their geometry and sorting continue to use canonical indices. History editors convert chosen displayed years to canonical values, submit a system revision, and the server validates world membership/revision and derives the source snapshot itself.

Extend disposable migration/service/browser coverage to legacy history, multiple reckonings, numbering boundaries/extreme years, foreign/default/source references, immutable arithmetic, retained archives, failed drafts, two-tab conflicts, position stability, privacy and desktop/phone screenshots. Rerun existing Worlds and catalog privacy checks, typegen/typecheck, focused lint, migration integrity and production builds. No Production migration, deployment or remote push.

## Independent deployment and recovery

Pass 2A is a complete year-reckoning feature and has no runtime dependency on Pass 2B or 2C. Every visible chronology action is operational. Worlds without custom reckonings use the canonical fallback; no author must configure anything before reading existing history.

Migration `0099_worlds_chronology.sql` follows `0098_worlds_pass_one`. It adds two populated-on-use tables and four nullable columns, with same-world foreign keys and validation checks. It has no data rewrite or backfill and introduces no environment variables, packages or external services. A fresh installation applies the entire committed journal in order; an existing installation first verifies its ledger and applies pending predecessors before 0099. The disposable rehearsal preserves original Worlds rows, all five date kinds, associations, timestamps and existing application data; a second migration invocation makes no changes.

For an authorized server release, verify the release/target/ledger, stage the production build, pause conflicting application writes and protect a verified backup, then run the established `npx drizzle-kit migrate` with the target environment's protected configuration. Activate the new application only after 0099 succeeds. Smoke-test existing history, a new reckoning, conversion, persistence and role-specific private/read-only access. This pass does not run that server procedure.

Prefer a reviewed forward fix. A code rollback does not remove these tables, metadata or ledger entries. The earlier Pass 1 read projection remains compatible with the additive schema, but an older history editor can change canonical dates without updating new source context. Pause history/chronology writes during an older-code fallback; retain metadata and migrate forward again before resuming authoring. If a database restore is required, stop writers, retain post-backup data for reconciliation, restore a verified backup and match the application and migration ledger to that restored point. Do not drop source columns or delete ledger rows as an improvised rollback. These operational steps require separate explicit authorization.

## Calendar evolution boundary (Pass 2A addendum)

A future calendar identity is a stable world-owned tradition, such as Imperial. Its historical versions carry immutable rule definitions and revision identities: Imperial I (ten 36-day months), Imperial II (twelve 30-day months), and Imperial III (revised leap rules). Those are distinct from this pass's year-number offsets. One calendar identity may have many historical versions; many calendar identities may coexist in the same world. A world's preferred display does not establish universal historical adoption.

Future adoption records will associate a calendar version with an independently authored culture/faction/region, a historical effective interval, and optional retirement/successor information. Effective intervals can overlap for different adopters. They must not imply that only one calendar or one version can be active worldwide. Reform records will link predecessor/replacement versions and the reason/effective position to existing History entries rather than duplicate historical accounts. Retired referenced definitions remain available; changing structural rules creates a new historical version rather than overwriting used rules.

Future precise dates need a separate absolute chronological reference in explicit elapsed units with a defined origin, plus version-specific mappings. It must distinguish actual position, calendar identity/version, printed/source date notation and precision. A conversion may yield an exact point, interval, several candidates (repeated labels), or no supported answer; it must expose that result rather than guess. No universal day count, Earth calendar or constant year length is inferred here. Legacy year-only entries keep canonical year/interval precision until an author explicitly supplies a supported finer reference; an upgrade must not select an invented first day.

For example, a change from ten 36-day months to twelve 30-day months may preserve 360 regular days, but that alone does not establish alignment: leap rules, year starts and an explicit anchor still matter. A transition to twelve 29-day months changes regular year length, so a year offset cannot supply an exact day conversion. If a reform prints the date after Month A day 20 as Month B day 1, chronological time continues while printed labels jump. Repeated dates require version/adoption context or an explicit occurrence disambiguator. This pass's offset conversion applies only to alternate numbering of the same canonical historical years; it makes no claim to convert those calendar dates.

Pass 2B authors functional calendar structures, including custom days/weeks/months, year lengths/leaps, seasons/holidays/recurrences, with definitions suitable for later immutable versions. Pass 2C adds historical versions, reform workflows, effective periods, adoption/coexistence and supported historical conversions. This pass adds no empty calendar/version/adoption/reform tables or controls and does not test those future features as operational. Its nullable, versioned year-reckoning source snapshots will coexist with a future explicitly discriminated calendar-version source and finer precision representation.
