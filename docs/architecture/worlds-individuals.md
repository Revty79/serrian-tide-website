# Phase 4B: individuals and personal accounts

Starting release: `3944a5418477ab868328683d7c746f98ba6c851a`. The inspected journal ends at 0116; this pass adds 0117 without changing earlier SQL or snapshots.

An individual extends `world_lore_identity` with the `individual` family. Its immutable typed source stores optional identity, existence, personality, knowledge, social and biographical fields. Only a name is required. Mechanical Characters, NPCs, Races, Creatures, Campaign state and government systems remain independent. Existing owner locks, request receipts, revision checks, source audit, archive/restore and read-only Administrator review apply.

Personal relationships reuse independent relationship identities and version-bound participants with original roles. Several parents, creators, companions or conflicting ancestry accounts coexist. Additional immutable relationship periods retain optional independent beginning/ending dates, ongoing/ended/unknown/disputed status, authored interpretation and perspective. No status is calculated from real timestamps. Explicit events use existing canonical History milestones; correcting one preserves its event ID and appends an immutable source. Existing History links support multiple entities and places without duplicate authoring.

Historical name/title accounts retain stable account IDs, optional dates, meanings, kind and perspective. Changing the main display name preserves the individual identity. Geographic associations retain the 4A-2 stable Atlas IDs, original source dates and protected flags; no map or route is generated.

The Individuals tab shares the mature lore persistence/editor contracts with Peoples while supplying a dedicated individual library, personal relationship creation, grouped optional detail and life-event shortcuts. References navigate to the appropriate workspace. Drafts and stale revisions retain the existing recovery behavior.

Individual sources always require explicit review before inclusion in a child timeline. A single early date on a biography cannot prove that later statements within it predate divergence. Relationship sources with periods and any lore source naming an individual participant likewise require review. This is a conservative whole-source decision, not a living-state simulation. Canonical History events are independently pinned and retain Bridge A boundaries: birth/achievement before 835 can be inherited while death at 840 remains excluded/pending and a child coronation at 845 stays local. Parent updates, newly available sources and nested branches retain explicit revision-checked adoption. Reviewers must deliberately remove unsuitable biography claims when authoring a local interpretation.

Protected individual fields, historical names, relationship periods and participant accounts are filtered before serialization. Private reputation starts protected by default. Pending/excluded sources and unadopted parent sources are withheld from ordinary knowledge. Protected participants are omitted from inverse discovery; a relationship with a protected participant is withheld entirely from ordinary metadata, preventing its name/count from revealing secret connections. Primary names requiring secrecy use whole-record protection. Milestones authored through a relationship with protected participants or periods are conservatively protected too. Private notes, custom sections, geography and canonical event visibility retain their existing server filters. Ordinary previews remain private owner/review tools and grant no public or Campaign access.

Limits remain 2,000 retained lore identities per World, 100 participants/geographic associations per source, 40 milestones/sections/names/relationship periods and 100 entity links per event. List pages contain 100 metadata records; optional narratives are loaded only for the selected detail. New child tables inherit the committed-source immutability guard and same-World family FKs. Existing ownership attribution FKs need no new account-deletion entries.

Release requires ordered migration 0117 after the actual target ledger is inspected, a verified backup, paused incompatible writers and authenticated owner/Administrator smoke checks. No configuration or external service is added. Old code cannot author individuals and may discard new personal metadata when rewriting older families; pause Worlds writes when recovering to an older release. Reverting code does not undo database sources or the ledger. Prefer a forward repair; restore a backup only with writers stopped and post-backup changes preserved for reconciliation. DEV/Production writes, push, deployment and Phase 4C remain separately authorized actions.
