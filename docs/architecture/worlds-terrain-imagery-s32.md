# Stage 3 Pass 2: terrain imagery and visual authoring

Authorized from `21cc99eec95779f61b8e2720120bf55e9405cf36`. Implement this complete vertical slice on main and publish through origin/main. No shared database writes, Production access, deployment, server restart, Studio, environmental simulation or subsequent pass.

The numerical terrain remains authoritative for shape, height, water level, coordinates and measurements. `terrain-surface-field.ts` reconstructs a smooth presentation from available root/refinement data, blending a narrow coverage edge into its known parent. Complete numerical neighborhoods are required; missing streamed detail retains the parent. Bicubic surface reconstruction never creates or saves measured samples. The sea mask uses interpolated saved heights.

`terrain-surface-art.ts` generates original coordinate-anchored surface artwork: stratified and jointed rock, scree, soil clods, grass ground-cover patches, sand ripples, explicitly selected pale/snow material, and shallow/deep water. Physical slope, numerical roughness, elevation above the actual sea and supported coastal proximity guide automatic mixtures. These are editable visual suggestions. They imply no climate, hydrology, forest, glacier or verified biome. Painting on submerged terrain remains retained but is masked by actual water.

`terrain-surface-painter.ts` generates viewport artwork tiles independently of elevation tiles. Visual LOD, artwork pixel dimensions and physical noise filtering respond to zoom/device pixel density. Tile resolution is not bounded by the numerical grid. Original procedural detail can show finer surface character while the numerical shape remains limited by accepted geography. A one-pixel sampling halo filters joins. Procedural phases are anchored to the World and periodic across wrapped longitude, never seeded per image tile. Texture keys include their actual numerical neighborhood and relevant vector strokes. Incremental rows yield to browser interaction. The texture cache has both count and 64 MiB pixel limits; only one active job allocates its pixel buffer. Switching render families releases the inactive family's textures.

`terrain-materials.ts` defines one sparse physical vector layer per map, independent of numerical source level. Ordered strokes carry material, radius in metres, strength and a bounded path. Later overrides blend over earlier work; erase blends back toward the current automatic assignment. Composition evaluates newest work first and skips fully hidden older contributions. There is no competing coarse/refined paint grid: every view evaluates these same World coordinates. Changing or regenerating heights updates automatic surfaces while preserving the manual vectors. Visibility/opacity affect the complete material layer, with neutral earth as the reference underneath; neither removes strokes or water. Locking prevents painting. Useful surface detail has a stated lower bound, separate from source sample spacing and screen magnification.

`terrain-material-client.tsx` provides its own undo/redo, completed-edit autosave, explicit saves, recoverable drafts, original-request retries, conflict export/reload and accepted version restoration. It stays mounted across numerical source changes. Material-only editing cannot enter numerical save/history paths. Browser recovery is map-scoped and optional storage failures are visible. The map retains its existing canvas and pose while modes, materials or appearances change.

Forward migration **0140** adds a material head and immutable accepted versions. Both reference existing World/map identity; material versions have independent revision and globally unique request identity. Existing ownership locks serialize saves, including competing first inserts. Retry lookup uses all accepted material versions, so a lost request can be confirmed after a newer save without overwriting it. Owner-only writes, explicit read-only Admin review, ordinary-data rejection, CSRF, bounded bodies, strict input/frame validation and restrictive attribution FKs use the existing website boundary.

Appearance v1 and its four styles remain valid. Appearance v2 deliberately admits Realistic Terrain through an expanded SQL constraint. The original `world_map_canvas.rendering` constraint and numerical revisions remain unchanged. Without 0140, Realistic Terrain previews still render, while material authoring/default saves clearly identify the required migration. Historical SQL is immutable; migration application to shared DEV/Production needs separate authorization.

Accepted material versions store sparse authored state, not full-World imagery. The initial bounded layer supports 4,096 strokes and 32,768 points, with up to 256 points per stroke and a 2 MiB request ceiling. This is one working visual layer, not a general multi-layer studio. Subsequent climate/biome recommendations can replace automatic mixture inputs without replacing the material/vector architecture.
