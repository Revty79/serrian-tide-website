# A5: separately approved migration through 0161

This is a procedure for review, not authorization to access or migrate the home server. A5 adds no database migration. The requested release requires all 162 exact entries through the existing additive `0161_atlas_expanded_numerical_terrain`. Normal website deployment refuses an older ledger and never migrates it.

1. Obtain a **separate owner-approved operation** identifying the exact PostgreSQL host/port/database/role, application release, existing three physical private roots, container/image, operator and maintenance window. Run the redacted [host preflight](deployment-a5-ubuntu.md). Verify actual PG18 identity/encoding/locale/extensions/TLS/privileges and immutable ledger hashes. Do not infer Production's migration state from DEV or a disposable success.
2. Fence public traffic/writers, jobs, importers, direct clients and file writers; stop the positively identified application and prevent automatic restart. The portability freeze requires zero other DB clients, not a maintenance HTTP 200. Retain the exact working container/image and protected config unchanged. Preserve browser-only user work before the window.
3. With explicit source profile and separately retained trust/signing/encryption keys, run the existing `environment inspect`, coordinated `backup`, `verify` and `seal` into NEW protected destinations. The source profile binds the actual DB identity and all three roots. Verify complete logical tables/schema/constraints/sequences/large objects/ledger, all files and hardlinks, signatures and unchanged source state. Retain an independently verified off-server encrypted copy. Never print URL/password/key/env values.
4. Independently open/verify and restore that pair into a **new disposable PG18 database and newly owned roots** with matching locale/extensions. Run `environment check`, independent native/history/image readers and representative restored account/permission/content reads. Stop test writers afterward. A checksum of the source archive alone is not an independent restore.
5. Rehearse the exact additive upgrade from the actual source ledger on that restored candidate. Capture its complete pre-migration snapshot, then use the existing explicit `environment migrate` with its exact environment/database confirmation, frozen attestation and pre-migration snapshot. This command intentionally accepts only an owned restored candidate with signed binding; do not weaken it to target unbound Production. Verify all previous rows, credential/session hashes, source identities, private files, history and all migration hashes; test transactional interruption, 0161 constraints and read-only new-release startup. Retain failures.
6. Present that **concrete rehearsal and paired recovery proof** for the owner to approve the exact live SQL operation or a separately approved new-environment promotion. If a same-database live migration is selected, the owner/operator must explicitly authorize a narrowly reviewed migration launcher against the freshly reverified target; the existing candidate command is not a generic Production bypass. Use the repository migrator, immutable journal order and one transaction for additive 0161, never schema push or edits to old SQL/ledger. Do not improvise this action from the website deployment block.
7. Immediately afterward query the actual target ledger for all 162 exact hashes/timestamps, inspect the four changed bounds and new immutable transfer tables/triggers, compare preexisting table/file/credential/session fingerprints and run read-only application/native-history reads. Record actual identity and results. Keep writers stopped on failure. Transaction rollback must leave the prior schema/data intact; never delete ledger rows or accepted geography to force compatibility.
8. Only after migration acceptance, re-run host preflight, review its new approval hash and authorize the website deployment separately. Do authenticated owner/tester smoke checks only after authorization to create/refresh sessions; then verify permissions, private content and relevant Atlas save/reload. Retain paired pre/post-upgrade recovery points and the former image/container.

Rollback assessment: 0161 is additive and does not resample terrain or alter existing accounts, but an old application does not understand large numerical sources or durable transfer records. A prior image is not automatically a safe writer after larger sources/new accepted data exist. Prefer a compatible forward fix. If an old writer must return, freeze and preserve new data, assess all changed records and reconcile explicitly. Restoring a former snapshot may discard accepted writes and always requires a separate owner decision and newly verified restore target; a code rollback does not reverse schema/data.

Isolated A5 evidence will combine the original portability's signed backup/independent restore/explicit older-ledger upgrade/native reads with A5's live-like 161-to-162 refusal/rehearsal and single-writer rollout tests. A4 separately verified populated 161-to-162 preservation and injected transactional rollback. These remain synthetic proofs until the actual source's locale, extensions, privileges, roots and data are rehearsed. Original DEV, clean DEV and both retained recovery points are outside this operation.
