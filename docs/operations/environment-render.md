# Future paid Render hosting

Design review only: no Render account access, subscription, service or disk was created. Final provider permissions, locale, capacity and SSH behavior must be rehearsed after separate owner approval.

| Setting | Reviewed direction |
| --- | --- |
| Database | Paid Render-managed PostgreSQL18, same region, private networking and verified TLS. New explicitly named database/role, never overwrite an existing instance. PG18 is supported according to [Render database documentation](https://render.com/docs/postgresql-creating-connecting) and [PG18 announcement](https://render.com/changelog/postgresql-18-is-now-available-for-render-postgres-databases). |
| Web | Paid Docker web service using reviewed runtime image, one instance, separate candidate service/environment; do not provision via this document. Disable automatic deploys during recovery and promotion. |
| Files | One persistent disk mounted `/var/data`; new signed environment child with terrain/artwork/raster children. All three `SERRIAN_*_ROOT` values point inside that child. No user data in Docker layers. |
| Start | Default image maintenance listener until restore and explicit approval; actual website runs through guarded `environment start`, on Render's supplied PORT. |
| Config | Private profile/trust/new auth-secret files outside Git, supplied through reviewed secret-file/runtime mechanism. Only target connection passed as `SERRIAN_INFRA_*`; no source/Production secret copied. Runtime profile hosting=`render` requires actual `RENDER=true`, preserving existing trusted Cloudflare client-IP behavior. |
| Auth | Exact canonical HTTPS origin and explicit allowlist; review any temporary domain individually. No wildcard Cloudflare/request-origin trust. Existing CSRF/session/rate-limit protections remain unchanged. |

Only disk-mounted paths persist; builds, predeploy commands and one-off jobs cannot access the attached disk. A disk is single-instance and prevents zero-downtime deploys. Plan downtime and one writer. This current local-filesystem design is suitable for that bounded topology, not horizontal scale. [Render persistent disks](https://render.com/docs/disks), [deploy stages](https://render.com/docs/deploys).

## Owner-controlled rehearsal

1. Review costs/capacity/region/locale/extensions/SQL privileges and provision only with owner authorization. A provider-provisioned NEW empty database can use `restore --precreated-empty true`; confirm no objects, clients or environment marker. The tool refuses incompatible locale/collation/extensions instead of relabeling data. PG18 support alone does not prove compatibility of a specific account/database.
2. Build the exact release using the repository Dockerfile, without any live database/disk. Render-injected build-context secret files are excluded by deny-by-default `.dockerignore`. Do not use secret build arguments. Build receives only the source Git commit; configure that non-secret argument explicitly. [Render Docker guidance](https://render.com/docs/docker).
3. Attach a paid persistent disk and start maintenance. Establish reviewed UID1000 ownership/private modes on NEW directories using supported shell access; do not expose disk contents or mount it at the service user's home. Validate available space, native immutable-reader access and hardlink support. SSH requires appropriate user/shell setup; the supplied Debian Node image has shell/core tools and does not use a distroless/root account. Verify access in the actual service. [SSH and shell](https://render.com/docs/ssh).
4. Freeze and capture the chosen source elsewhere. Independently verify and encrypt the complete pair. Transfer the `.stenv` file to a protected directory on the RUNNING disk-backed service using documented SSH/SFTP, e.g. `scp -s LOCAL_ENCRYPTED_FILE SERVICE@ssh.REGION.render.com:/var/data/transfer/NEW_FILE`. Review SSH host keys and exact destination first. SFTP resumable `reput`/`reget` may continue the same encrypted file. Provision recovery keys separately through an approved secure channel; never put them in the image or beside publicly downloadable files. A build or imaginary automatic Docker copy cannot transfer persistent user files. [Supported transfer](https://render.com/docs/disks#transferring-files).
5. In the running service shell, `open`, `verify`, `restore`, `check` with the explicit private candidate profile and PG18 clients. These commands must execute on the disk-attached runtime, not predeploy or one-off compute. Keep decrypted staging private and account for archive+extraction+restore headroom. Restore intent/signatures remain on the persistent disk. No shared destination is claimed automatically.
6. Generate the environment-bound new auth secret. Apply explicitly approved additive migrations after a verified pre-upgrade snapshot. Start website on loopback from the same stamped release for local shell HTTP checks, authenticate and inspect actual retained content. Keep maintenance as the public listener until validation is accepted. Do not run two application writers.
7. Create the signed cutover plan with a verified distinct former-Production snapshot. Owner explicitly approves plan SHA, `--listen 0.0.0.0` startup and service/domain/DNS change. Configure the eventual start command with that exact plan/profile approval. A restart verifies environment/build identity; subsequent reviewed releases need a newly prepared plan using a frozen snapshot of the current environment and a separate rollback point.
8. Review Render domain/TLS/PORT and exact Better Auth origin, user/admin/Canon/privacy behavior and actual client-IP rate limiting. Keep old Production frozen and recoverable. Maintain independently encrypted off-platform backups of BOTH DB and files with keys separate. Render database PITR/logical backups alone do not pair the private filesystem. [Render Postgres backups](https://render.com/docs/postgresql-backups).

Unverified until an authorized Render rehearsal: selected plan/space, actual managed DB privileges and locale/extensions, external/internal TLS/CA details, disk UID/modes/hardlinks, SSH/SFTP permissions and interrupted transfer, restored website in Render runtime, domain/private ingress/egress, operational health/restart command and real proxy client-IP chain. No paid-resource-ready certification is claimed from local Docker CI.

If future concurrent instances or disk capacity make this topology unsuitable, plan a separately reviewed object-storage adapter preserving content-addressed immutable keys, hashes, versions, original retention, authenticated access and coordinated snapshot semantics. That future migration is not implemented here.
