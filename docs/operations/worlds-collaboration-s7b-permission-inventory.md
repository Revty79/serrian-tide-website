# Stage 7B initial permission inventory

Audited starting checkpoint: `881e18bf05e38eaefac50b6f8d54f64e86970578`. This inventory precedes implementation. It describes the existing code, not completed Stage 7B protection.

| Boundary | Existing authority | Gap and required correction |
| --- | --- | --- |
| Worlds entry and creation | `server-access.ts`, Worlds layout/pages and `access-directory.ts` require G.O.D./Administrator. `world-service.ts:actor` applies the same role gate. | Invited eligible accounts need authenticated entry and an invitation inbox without global creator powers. Creation must retain its current role requirement. |
| Private World identity | `world-service.ts:readWorld` selects the owner, except explicit Administrator review. `lockOwned` locks the real owner row. | Keep private defaults and actual ownership. Add current accepted grants and distinguish scoped content writes from owner-only settings. Unreviewed operations must remain owner-only. |
| Registry | `listWorlds` selects owned Worlds, or other owners for Administrator review; the gallery filters a complete list in the browser. | Add an invited collection and a server-paginated Administrator registry across all owners, with indexed filters/sorts, identity/status/participant metadata and explicit management. |
| HTTP and sessions | `worldRequest` checks the authenticated session, same-site mutation Origin/Host, ordinary read-only previews, retired routes and private/no-store responses. | Retain these checks. Carry authenticated per-request World context and per-tab editing credentials without trusting a role, user ID or lease fence from a request body. |
| Core mutations | `worldWriteTransaction` checks global creator eligibility and locks the owner World. Several World/History functions also call `lockOwned` directly. | Inventory every caller and add explicit operation scopes. Recheck current grant and editor fence inside the same locked transaction. Keep World archive/restore, sharing and ownership controls separate. |
| History and timekeeping | History index/version, branching, calendars and chronology use World guards and existing ordinary/protected projections. | Scope-filter records, counts, references, sources and selectors before serialization. Preserve immutable attribution and unknown coverage. |
| Peoples and related sections | The shared Peoples service implements societies, Individuals, politics, Organizations, Cosmology and Stories, with existing family and visibility rules. | One endpoint does not mean one permission: filter each real family, detail, source, list, count and reference by its section. Preserve protected-source filtering. |
| Towns, Shops and Places | World Town/business services and native Town Maps use owner guards and permanent geographic/commerce identities. | Share only authorized World content. Keep commercial catalog/private account operations independently authorized, and withhold creator notes and unauthorized linked families. |
| World/regional terrain | Terrain, tiles, refinements, raster, materials, hydrology, environment, artwork, labels, styles and hierarchy use World guards; ordinary native map requests are currently withheld. | Explicitly authorize shared map reading independently from editor control. Apply the same scope to numerical bytes and source versions. Do not enable the retired Atlas or alter terrain/rendering engines. |
| Interiors and Underground | Floor and underground services use owner guards. Underground already has `ordinary`/`secret`/`god-only` feature visibility and `redactUnderground`, including attached-geometry filtering. | Preserve these visibility rules and separate private creator content from a section grant. Filter connections and prevent a redacted editor submission from deleting hidden work. |
| Craft, decks and entrances | Native craft service checks the owner World and native source/arrival identities. | Authorize craft scope, current editor fencing and both ends of cross-family routes without inferring new relationships. |
| Historical native appearances | Native history context/service/write/request/comparison adapters use owner/review guards, immutable component/source pins and exact request recovery. | Require the underlying family and historical permissions together. Reauthorize original requests, comparisons, related records and retained source bytes after revocation. |
| Private assets and templates | Asset library belongs to a creator. Non-owner Administrator review is already limited to versions actually pinned by the selected World. Asset images recheck World access and usage pins. | Reuse immutable pins; sharing one World must never expose the owner's whole library or another World. Check current grants on every download and family-specific usage. Do not let contributors mutate another creator's private library. |
| Discovery and contextual navigation | Stage 7A discovery composes actual History, lore, place, society-time, Realm-map, Campaign and native-map relationships. | Filter both sides of every relationship by scope and visibility before returning labels, counts, sources, choices or destinations. Preserve World/timeline/year/camera and drafts. |
| Editing concurrency | World row locks and resource revisions serialize transactions and reject stale resource revisions, but no durable editing lease exists. | Add session-bound, per-tab, expiring leases with monotonically fenced writes, deliberate release/request/approval/reclaim and recovery-preserving UI. A global Editor flag is insufficient. |
| Administrative review | Explicit `review=1` allows an Administrator to read another owner's World. Normal owner writes remain owner-only. | Keep review read-only. Add distinct audited access-management actions; no impersonation, ownership transfer, unrestricted content editing or deletion. |
| Account lifecycle | `user-account-delete-plan.ts` inventories restrictive World ownership, immutable authorship, native sources, assets and audit references. | Include new invitation, grant, lease and audit relationships; retain accepted authorship independently from membership. |

The implementation must combine global account eligibility, actual World ownership or accepted invitation, requested section/resource scope, protected-content permission and the current editor lease. Campaign membership, knowing an ID, an old page and a pending invitation confer no authority.

This is an initial audit. The completion matrix and report must separately identify actual implemented guards, direct-resource tests, usable browser journeys, retained failures and remaining limitations. Stage 7B remains incomplete until every relevant endpoint and resource family is covered and final validation/publication is verified.
