# Ubuntu 24.04 / Docker operator procedure

This is a new-candidate procedure, not permission to change the existing home server. Actual owner mounts, services, credentials and source locale remain uninspected. Keep the current Docker approach; add explicit persistent mounts and reviewed operator commands. Never build over a live environment directory.

1. Obtain owner approval for a specific maintenance window/source/destination. Inventory the current container's three resolved storage roots and PostgreSQL identity using non-secret operator configuration. Do not infer a volume name from this repository. Complete the [freeze/backup checklist](environment-portability.md) before any live move.
2. On a clean release at the reviewed commit, build `Dockerfile` with `--target runtime --build-arg SERRIAN_BUILD_COMMIT=EXACT_COMMIT`. Run normal CI first. Node22, PG18 clients, TLS CA certificates and Linux dependencies are included. No runtime database, secret or data mount is used during build. `.dockerignore` is deny-by-default; private env/storage/artifacts are absent.
3. Deliberately create a NEW protected operator parent and candidate parent on persistent server storage with adequate free space. Container UID/GID1000 must own the new roots/files it writes (0700/0600). Do not recursively chown existing owner storage. Snapshot keys/configuration stay separately protected and outside the image. Keep DB ports private; use verified TLS for non-loopback connections.
4. Mount the NEW persistent parent at `/var/data`, not under `/app` or `public`; restore creates `/var/data/ENV_NEW/{terrain,artwork,raster}` and signed environment receipts. The private destination profile uses those exact in-container paths, its new named PG18 database/role and `/app` release directory. PG18 lives outside the application container, following the existing server arrangement. Provision the new SQL role/database separately as documented; do not add an unsolicited second live database service.
5. Run `verify`, `restore`, `check` through a task-owned operator container using the same image, protected operator configuration and persistent destination mount. Supply only the NEW explicitly named connection variable. Never mount the owner Docker socket or the whole server filesystem into this container. Container replacement/image rebuild must retain the same `/var/data` bind mount and matching database.
6. DEV: run `isolate-dev`, generate a new secret and use loopback origin. For a production candidate, generate its separate secret. Apply any explicit additive migrations from a verified candidate recovery snapshot. Start in a private validation context and test real login, permissions, saved history, terrain, images and raster. Full `check` occurs before login writes; later `inspect`/frozen backup verifies the current state.
7. Review [Compose example](../../ops/compose.candidate.example.yml). It uses an exact image tag, UID1000, read-only image, writable persistent data, private read-only config, writable temporary/cache mounts and a host-loopback port. Loopback-only startup inside a bridge container is accessible via `docker exec` for validation; host mapping becomes useful only after explicit signed-plan `0.0.0.0` startup approval. No reverse-proxy switch is automatic. In production add your reviewed restart/health/log policies; do not accidentally restart the former writer.
8. Prepare and review the exact cutover plan. After owner approval start the candidate and deliberately update the existing reverse proxy. Verify actual public TLS origin, Better Auth allowlist, per-client rate limiting, private assets and ordinary user/admin access. Retain old database, mounts, code and separately protected keys. Use the rollback procedure for any new writes.

Health: image default `maintenance` returns generic `GET /health`200 and other routes503, with no app/DB access. That only proves the maintenance listener. Running candidate health requires process/HTTP checks plus `inspect`/restored-data verification and authenticated real content reads; a200 login page alone cannot prove correct storage. Do not run expensive full snapshots on every liveness probe. Monitor PG reachability, private mount writability, free space, storage integrity errors and backups. Keep logs private and avoid verbose SQL or secret environment dumps.

The Docker recovery CI uses an isolated Ubuntu24.04 runner and PG18 server inside a new container with `--network none`. It does not reach any server, shared database or Render account. The delivery report distinguishes this smoke evidence from verification of the actual Ubuntu host. Cross-platform restoration uses logical archives; physical PG clusters are never copied between Windows and Linux.
