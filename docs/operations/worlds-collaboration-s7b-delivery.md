## Ownership and access

A World keeps its original creator. Global Administrator/G.O.D./Player roles establish product eligibility; ownership, an accepted invitation or an explicit canon publication then establishes World access; explicit section scopes and protected-content permission determine each readable resource; a live session/tab fence determines content-writing authority. An invitation grants no global creator role, Campaign membership grants no World access, and an ID or retained URL grants nothing.

Seventeen section scopes cover Overview; History/timelines; timekeeping; Peoples; Individuals; politics; Organizations; Cosmology; Stories; Towns/Shops/Places; geographic Atlas; interiors; Underground; craft/decks; historical appearances; assets/templates; and Campaign associations. Historical appearances also require History and the underlying map family. Existing protected records, creator notes, private fields, source graphs and hidden underground details remain restricted unless the owner explicitly includes protected material.

Owners target exact registered usernames through bounded, rate-limited in-app invitations. Pending, accepted, declined, revoked and expired states retain identity and timestamps; invitations expire after seven days. Owners review scopes before sending, can change/suspend/restore/revoke participants and can withdraw pending invitations. Exact request receipts prevent uncertain acknowledgements or old invitations from recreating access. Participants cannot manage grants.

## One active editor

All 60 active World/Administrator route modules carry the centralized request context. Explicit content scopes cover 106 reviewed calls in 46 service files; unreviewed operations remain owner-only. The server serializes content writes on the World row, rechecks current roles/grants/session and validates the exact session, tab UUID, random token digest, monotonically increasing fence and database-clock expiry. A 120-second lease renews every 55 seconds while the active tab is visible. Requests, owner-approved handoffs, voluntary releases and explicit owner reclaims preserve accepted versions. Late fences, expired sessions and expired transactions fail; expiry after work begins rolls the transaction back.

World client requests also carry the expected actor identity. The server compares it with the actual authenticated session before running a request; a stale tab from another account gets 409 before a mutation or private response. This header is an expectation, never an authorization identity. It is attached only to same-origin requests.

The new holder reads current accepted map sources and verifies the fence before editing is enabled. Existing map packets retain their original revision and exact request bytes. Loading control does not force a recovered map packet to be discarded before it can retry. Stale revision checks still apply. Draft storage is account-bound; ownership-verified legacy packets continue in place without duplicating large local-storage packets. Export and deliberate discard remain available for unreadable access packets. No lease token is persisted in device storage. Same-World map destinations preserve the in-memory tab and fence; accepted navigation reopens the native destination through the existing draft guard and refreshes its dated parent even when the parent query is unchanged. Map Back/Forward changes use that guard; another World or site uses ordinary document navigation. This uses the supported [Next.js native History API](https://nextjs.org/docs/app/getting-started/linking-and-navigating#native-history-api). Fresh resource authority updates only `canEdit`/reason, retaining original source revisions and drawings. Unchanged authority keeps object identity.

## Canon and personal variations: owner supplement

The owner explicitly selected **whole Worlds** for Administrator canon marking, then required every Player to be able to use canon as a pattern for personal timelines, maps and stories without changing canon. This supplements the private-by-default brief: only an explicit Administrator canon decision publishes ordinary World content to signed-in eligible Players. Protected notes, hidden records, private source material and Campaign associations do not become public through this action. Administrator review still sees all Worlds and protected content, separately from mutation authority.

While canon is published, every non-owner participant receives the same ordinary read-only view, including an account with an older narrow/protected invitation. Protected material stays with Owner and privileged Administrator review. Original invitation settings remain stored and resume after canon withdrawal; no narrow protected grant is widened across public sections.

Canon status is a revisioned, immutable decision in the existing access audit; the World row lock serializes it with every content write. Marking retires the active editing fence and blocks original content edits even for the owner. A separate, confirmed Administrator decision can withdraw canon, restoring existing private access rules. Neither action transfers ownership or rewrites World content. Notes, real actor and exact-request identities are retained. No extra schema or migration beyond the additive 0159 is introduced for canon.

The signed-in canon library uses bounded 50-row pages and rechecks current decisions. Every eligible Player can create a **private independent variation** through that narrow route without acquiring the global G.O.D. role or general blank-World creation. It snapshots the source opening pages and active ordinary Primary History, remaps World/record/era identities, strips private notes and source dating links, preserves canonical World-year values/unknown dates, and records original version provenance. The new owner can branch timelines and author maps/stories through the normal fenced editors. Canon maps and lore stay available as read-only references; native map geometry, binary assets, other timelines, linked lore/commerce identities and private libraries are not cloned into the personal World. The UI describes this starting point explicitly. Later withdrawal of canon does not delete a personal variation or rewrite its snapshot. Access to the source's current view still follows current permissions.

Existing catalog canon roots also reject ordinary authoring through the central shared-library guard. The Race, Creature and Item variation paths use a distinct pattern permission so copying an authorized canon pattern does not require permission to change its original. Existing product entry/creation rules outside Worlds are retained; this is not a redesign of the Heavens catalogs.

Focused canon unit, actual authentication/UI, Player variation, original-source preservation, byte-identical lost-acknowledgement recovery and withdrawal checks pass against production candidate 34. An older narrow/protected invitation cannot block ordinary canon or broaden private access: the ordinary view applies during publication and the unchanged invitation settings resume after withdrawal. Mismatched expected/session actors are denied before canon decisions, private variation creation and reads. These additions are included in the verified application commit below.

## Using the new controls

Administrators: open **Worlds**, then **Administrator review**, open the World, choose **Inspect World access and record review**, then review the whole-World canon publication/lock, write a decision note and confirm **Mark whole World as canon**. The same separate action can withdraw canon. Normal review remains read-only and sees all protected World content.

Players: open **Worlds**, then **Canon Worlds**, choose **Use as a pattern**, name the private version and create it. Open that version to use its own timelines, stories and map editors. The original canon World is a read-only reference. The creation screen describes which ordinary history is copied and which maps/libraries remain references.
