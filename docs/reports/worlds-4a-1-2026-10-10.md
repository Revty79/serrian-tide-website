# Worlds Phase 4A-1 — peoples, origins and historical milestones

Starting commit: `9bf7391d3ac3f7c7f2390d0c8f1dbae5cebc4480`. This report belongs to the local commit containing **Complete Worlds peoples and historical milestones 4A-1**; the completion response provides its exact SHA.

This is the first of the two approved, independently deployable Phase 4A checkpoints. It does not declare all of Phase 4A complete. No remote push, deployment or configured DEV/Production migration is included.

## Completed increment

The private World workspace now has working Races/species, peoples, contradictory origin accounts and custom multi-participant relationships. Simple identities require no invented biology, origin or date. Optional domain fields, attributed accounts, unresolved authored references, custom sections, protected knowledge, ancestry and paradoxical relationships support more detailed authoring. Creation, editing, name search, family filtering, pagination, linked-record navigation, archive/restore and explicit conflict recovery work on desktop and a native-touch phone.

These identities have separate typed content tables and immutable versions. The small shared registry supplies stable, same-World reference addresses and creation attribution; it does not replace the distinct domain models. Primary, alternate and nested timelines pin immutable sources. Parent changes and newly available sources require deliberate acceptance. Local interpretations preserve their original sources, and pending/excluded accounts cannot be silently treated as effective facts.

Entity milestone authoring saves atomically into the **existing History entries and immutable History versions**. A corrected date updates the same stable event identity and appends its revision. Metadata-only entity edits do not invent new events. Custom event types and validated entity categories are stored with version-bound, indexed references. Events can link several entities or an existing Atlas place. History retains full-account reading and direct navigation to the original entity, with the appropriate timeline context. Entity readers link back to milestones and can open the exact immutable historical account they cite.

The new interfaces reuse shared appearance variables and field guidance. Failed saves retain drafts; a successful save followed by a failed list refresh remains visibly acknowledged. Ordinary-knowledge preview strips protected records, sections, notes and references on the server before serialization. No Player/public World access was introduced, and Administrator review remains explicit and read-only.

The [architecture contract](../architecture/worlds-peoples.md) describes provenance, authorization, bounds and future reuse.

SQL guards retain identity/provenance, make committed versions and their components immutable, require complete typed content, enforce owner attribution, and protect revision progression and append-only decisions. Account deletion now inventories the three new restrictive attribution references.

Disposable rehearsals installed the complete journal, upgraded populated 0113 data to 0114 and reapplied migrations safely. Existing World, historical-date, primary/alternate/nested source, calendar, Atlas/dungeon and Campaign-context/home/audit projections were preserved; new entity tables began empty. Historical dates retain the existing five precision forms, reckonings and saved calendar notation. No date was inferred.

## Deployment readiness and recovery

No environment changes, email provider, external generation service or new credentials are required. 4A-1 works independently of 4A-2 and 4A-H; future controls are not left active or blocking current authoring.

For a separately authorized deployment:

1. Verify the server identity, configured database and actual migration ledger. Read-only ledger verification here refused the configured non-loopback/non-`_dev` target before connecting; current DEV/Production ledgers remain unverified.
2. Take and verify a recoverable database backup. Apply any missing committed predecessors in journal order through 0113, then apply 0114 using the established Drizzle migration procedure (`npx drizzle-kit migrate`). Do not edit published SQL, reset the ledger or skip predecessors.
3. Build and activate this checkpoint using the existing controlled server procedure. Smoke-test sign-in/recovery, private World access, desktop/phone record creation, canonical milestone correction/navigation and an alternate-timeline source decision.

Reverting application code does **not** reverse 0114. Preserve additive tables, retained versions, bindings and the migration ledger. An older application can read existing legacy data, but older World writers do not preserve new entity bindings/protected metadata or pin the new entities. Pause incompatible World writes and account-deletion workflows during rollback; prefer a reviewed forward fix. A backup restore requires maintenance, verification and reconciliation of writes made after that backup. Do not drop historical entities or rewrite source rows as a rollback shortcut.

**4A-1 is ready for a separately authorized GitHub push and controlled server deployment. There are no remaining implementation blockers for this checkpoint.** No push or deployment was performed. Target identity/ledger and backup verification remain deployment preflight requirements; 4A-2 and 4A-H remain project work, not runtime dependencies of this checkpoint. The environment does not expose a reliable remaining coding-allocation meter.
